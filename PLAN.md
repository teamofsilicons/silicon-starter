# Silicon Starter implementation and launch plan

This plan is based on `UNDERSTANDING.md`, `IAM.md`, Silicon Stemcell's `UNDERSTANDING.md`/README, Silicon Omni's `UNDERSTANDING.md`/README, the bundled IAM client/API documentation (`client/connecting`, `client/login`, `client/tokens`, `client/webhooks`, `client/testing-environments`, `client/obo`, `api/applications`, `api/obo`, `api/testing-environments`, `batch-login`, `storage`), and the Space Station client/table contract.

## 1. Repository shape

A Rust workspace will ship one stateless library and two consumers:

- `crates/core`: starter identifiers, `silicon.yaml` validation, release/version rules, git/archive manifests, search query model, discussions, stats, update policy, and telemetry event envelopes. Validation requires a base-directory `silicon.yaml`; files/folders are arbitrary and empty folders receive `.siliconkeep`.
- `crates/client`: HTTP client and IAM/Briefcase/Space Station integrations. It owns no mutable server state and is usable by the daemon and CLI.
- `crates/daemon`: the always-running local worker. It keeps one Space Station/ IAM update connection per machine, checks the CLI and downloaded starters hourly, and performs safe local update commits.
- `crates/cli`: the `starter` binary. Help is a command tree with exact errors, `starter iam --json`, `starter login <SLT>`, `starter login status --json`, webhook/unhook, bug report, and all starter lifecycle/search/discussion/star/fork commands.
- `crates/api`: Axum backend with versioned HTTP routes, authorization, webhook verification, Postgres repository, Briefcase OBO gateway, semantic search, and telemetry.
- `frontend`: SolidJS/Vite web subset for carbons: organization rail, browse/search, starter detail, versions, `silicon.yaml` block viewer, discussions, stars, fork, release notes, and IAM callback.

The API and CLI use the same core request/response types. Contract version is `v1`; startup negotiates IAM's API version and exposes an API compatibility endpoint. No raw source bundle is shipped to consumers; release artifacts are signed binaries/install scripts.

## 2. Data and storage

Postgres is the metadata source of truth with `pgvector` for semantic search. Tables cover organizations visible to the app, starters, immutable commits, published releases, release files/manifests, downloads/updates/stars, discussion nodes, webhook event dedupe/version watermarks, sessions, and telemetry outbox. Every publish stores the complete git archive and `silicon.yaml` reference plus release notes; versions are monotonic `Y.X` and never rewritten.

Starter bytes and `.git` history live in Briefcase. Draft/pull storage uses the caller's private app folder. Public release storage uses an organization public path (`public/starters/<org>/<starter>/<version>/`) and anonymous link access. The current app already has OBO `entries.list`, `files.create`, and `files.read`; before implementing public release writes, the app scope request will add `folders.create` and the critical `link_access.update` endpoint. If that review is not approved, the backend will fail closed with a clear “public release storage scope pending” error rather than silently making a private release.

OBO requests use a fresh single-use proof per exact method/path/body/org, SHA-256 over the exact body bytes, and `x-iam-obo-access-proof`; proof verification is never retried after an ambiguous consume. Long uploads use Briefcase reserve/commit/status/cancel and stable operation IDs.

## 3. IAM and session security

The canonical app is `tos>starter`. Browser login redirects to IAM with `app_id` and a callback state cookie; no org ID is put in the URL. The callback receives only the two-minute, one-use SLT. The backend exchanges it with Basic app credentials and an idempotency key, introspects immediately, stores the rotating refresh family server-side, serializes refresh, and atomically replaces token pairs. The browser receives only an opaque starter session cookie.

CLI login accepts only an SLT generated by IAM, stores its own session under `$SILICON_HOME/.starter`, and never asks for IAM credentials. `starter login status --json` reports the current app authorization. Org access is limited to the memberships the user selected in IAM; every request rechecks/introspects current authorization when its projection is absent or stale. Testing uses one IAM environment key throughout and keeps test Postgres/Briefcase data partitioned by environment.

The deployed IAM app currently has a pending critical directory-scope review and a pending production webhook approval. The build will use currently effective self scopes until review completes, submit the directory/public-storage scope request with its rationale, and approve the webhook after the endpoint is live using the owner step-up flow. The backend will not assume unapproved directory fields.

IAM webhook handling reads raw bytes, checks five-minute timestamp tolerance, selects the key version, verifies `v1=` HMAC-SHA256 in constant time, deduplicates event IDs atomically, orders aggregate versions, acknowledges quickly, and processes asynchronously. Test envelopes are verified and routed by the test key, then redacted from logs and telemetry.

## 4. CLI and daemon behavior

`init` creates git `main` and `.gitignore`; `new` creates the starter and mandatory `silicon.yaml`; `commit` stages all non-ignored files; `push` requires authorization and is never available for downloaded starters; `pull` is editable and never auto-updated; `download` is read-only, auto-updated by default, and pins on `@Y.X`/`@commit`.

Publish accepts `latest` or a unique/complete hash prefix and a higher `Y.X`; history is immutable. Revert creates a new commit after a merge. Update commits local changes first, attempts a normal git merge, then calls Silicon Omni one provider at a time if needed. Omni selection uses `dial`/chooser keys and never a hardcoded model map; each provider reaches idle/END before the next repair attempt. No conflict state is shown to users and no half-merged tree is persisted. Pulled developer starters never auto-update.

The daemon starts lazily, checks for updates hourly, uses one websocket/subscription for all registered silicons on the machine, preserves local history, and drains accepted work on shutdown. It never modifies `silicon.yaml` during interpreter updates. Telemetry is opt-in by default, uses the four app-specific Space Station table keys, sanitizes secrets/files, and honors `SPACE_STATION_TELEMETRY=0`; missing keys disable telemetry without preventing startup.

## 5. API and web surface

The backend exposes health/version, IAM callback/webhook, organization list, starter list/detail, semantic search, commit/release history, archive download, discussions with nested replies and release-update blocks, stats, star/unstar, fork, pull/download manifests, publish/push, update policy, and a telemetry proxy for frontend analytics/events. Public routes are anonymous only for public released data; private routes require an active IAM session and selected org membership.

The SolidJS app calls only these versioned routes, never sees app secrets, table keys, IAM tokens, or Briefcase proofs, and handles the `#slts=`/`?slt=` callback by immediately posting the SLT to the backend and clearing the URL. It renders loading/error/empty states, keyboard search, accessible controls, and a distinct color-coded `silicon.yaml` block view.

## 6. Verification and release

Before any deployment: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test --workspace`, release builds for Linux ARM64/x86-64, `npm ci`, `npm run build`, API smoke tests for public/private/auth/error paths, IAM test-environment flow (selected/unselected org, refresh/revocation, webhook, OBO, production/test rejection), and a local CLI update/merge self-check.

Backend deployment uses an encrypted S3 release bucket, Secrets Manager for IAM/Briefcase/Space Station/Postgres credentials, a dedicated ARM64 EC2 service in the existing AWS VPC, private RDS PostgreSQL with automated backups, and the existing HTTPS ALB after a new ACM certificate and host rule are provisioned. The service is fronted at `backend.starter.teamofsilicons.com`; Namecheap receives the ACM validation and backend CNAME records.

Frontend deployment uses Vercel, then attaches `starter.teamofsilicons.com` and adds its Namecheap CNAME/verification records. GitHub receives the source and signed binary release. Live health checks and a real IAM callback smoke test run after DNS/ALB propagation; any provider review or DNS validation that remains pending is reported explicitly with the exact next command.
